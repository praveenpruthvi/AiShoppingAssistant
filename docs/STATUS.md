# Development Status

## Current milestone

Milestones 0–2B2 and 3A are closed. Milestone 2C1 — the store-scoped assistant search index and the production `OpenSearchProductDocumentWriter` — is implemented and verified: per-store prefix/alias/physical-index naming, the fail-closed `AssistantSearchClientInterface` (production OpenSearch client + unavailable fallback), the versioned `dynamic: false` product mapping with `knn_vector`, enriched `IndexedProductDocument` payloads, bounded embedding enrichment, two-phase writer lifecycle with atomic alias activation and idempotent abort, config-driven index prefix, and the extended sanitized indexing exception taxonomy. The final 2C1 safety hardening verifies new physical index `_meta` before activation, proves every existing alias target by strict name parsing plus `_meta`, rejects mixed/unproven aliases and interleaved-store processing, hardens bulk and cluster-info parsing, and validates normalized endpoint/auth config through an injectable OpenSearch builder seam. Milestone 2C2A adds the transport-independent incremental indexing core: one positive product id, active-store iteration, disabled-store skip, exact alias compatibility proof, idempotent delete for missing/ineligible products, complete-document no-op, embedding-content vector reuse, and fresh embedding when reuse cannot be proven. Milestones 2C2B1, 2C2B2A, and 2C2B2B1 add staged Magento queue XML, a durable product-id-only work ledger, a staged durable scheduler, a ledger-coordinated single-message consumer, allowlist retry policy, bounded cron wake-up recovery, and durable full-rebuild fencing with post-cutover recovery wake-up. Production incremental scheduling intentionally remains unavailable until observer/mview capture, reconciliation, and final activation. Hybrid retrieval, reranking, chat (primary LLM) generation, storefront UI, and guardrail classification remain out of scope.

Milestone 2C2A:

- `Api/Indexing/ProductIncrementalIndexerInterface` — transport-independent public boundary for reconciling one explicitly validated positive Magento product entity id. It has no HTTP/controller/session/customer/current-store/ObjectManager/queue dependency and keeps no in-memory processed cache.
- `Model/Indexing/IncrementalProductIndexer` — iterates active frontend stores, reads explicit store-scoped general/indexing config, skips disabled stores without OpenSearch or embedding calls, captures the frozen embedding config, proves the exact store read alias has exactly one assistant-owned compatible physical target, reloads the current Magento snapshot, normalizes through existing catalogue policy, and reconciles the deterministic store document id.
- Incremental target validation: canonical alias only, no wildcards, exactly one target, strict assistant run-name parsing, exact `_meta`, assistant marker, matching store/website/physical index, valid run id/token, current schema/mapping version, and frozen embedding dimensions/fingerprint/base-URL hash. Failures surface as sanitized `incremental_target_invalid`.

- Stable new sanitized codes/classes: `incremental_target_invalid` and `index_document_state_invalid`.

Milestone 2C2B1:

- `MagentoIncrementalProductIndexScheduler` is a staged, directly injectable queue publisher. It validates positive integer ids, validates a list completely before publishing anything, deduplicates and sorts deterministically, publishes only one product id string per message, and converts unexpected publisher failures to sanitized `incremental_queue_publish_failed` without leaking raw broker details.
- Queue transport is declared through `communication.xml`, `queue_publisher.xml`, `queue_topology.xml`, and `queue_consumer.xml` using topic/queue/consumer `aavirbhava.ai_shopping_assistant.product.incremental_index`. The publisher leaves connection and queue name resolution to Magento so AMQP, STOMP, and database-backed installations can use their configured transport.
- `IncrementalProductIndexConsumer` validates the received payload as one positive id, invokes `ProductIncrementalIndexerInterface::process()` exactly once, rejects malformed payloads with sanitized indexing exceptions, and lets indexing/provider/OpenSearch failures propagate from the handler. Magento's default consumer rejects ordinary handler failures with `requeue=false`, so this is not durable retry behavior yet.
- Existing `ProductIndexer::executeFull()` behavior is unchanged; row/list/mview execution continues to call the scheduler contract, which remains the fail-closed `UnavailableIncrementalProductIndexScheduler` production preference until 2C2B2 supplies bounded durable recovery and reconciliation.

Milestone 2C2B2A:

- `aavirbhava_ai_incremental_product_work` stores one durable, coalesced row per product id with latest requested generation, nullable claimed/processing generation, state (`pending`, `queued`, `processing`, `retry_wait`, `complete`, `blocked`), bounded attempts, next attempt, opaque lease token/expiry, sanitized last error code, and timestamps only.
- `DbIncrementalWorkLedger` records changes, atomically claims due work, completes only exact claimed-generation/lease pairs inside row-locking transactions, records retry or terminal state without raw errors, recovers expired leases with attempt accounting, and supports bounded deterministic due-id selection.
- `DurableIncrementalProductIndexScheduler` is staged and directly injectable. It validates, deduplicates, sorts, records ledger work before queue publication, and leaves recorded work due if publication fails. It is not the production scheduler preference.
- `IncrementalProductIndexConsumer` now treats queue messages as wake-ups: it validates the id, holds a Magento product worker lock across claim/index/finalization, invokes the incremental core once only for a claim, records success/retry/blocked state, propagates ledger persistence failures separately, and returns safely for stale, duplicate, or already-locked messages.
- `IncrementalFailureDispositionPolicy` retries only allowlisted transient `OpenSearchBackendUnavailableException` failures, with at most five attempts and 60-3600 second deterministic backoff. Unknown, validation, safety, configuration, malformed, provider/refusal-like, and incompatible-index failures are terminal/blocked.
- `IncrementalWorkRecovery` runs from cron every five minutes, takes a Magento lock, recovers expired leases, marks up to 50 due rows as queued, and republishes product-id wake-ups without indexing or embedding. Expired leases consume bounded attempts unless a newer generation was scheduled, in which case the newer work is released fresh.

Milestone 2C2B2B1:

- `aavirbhava_ai_rebuild_fence` stores a singleton full-rebuild fence with only active state, opaque owner token, lease expiry, and timestamps; active and inactive row shapes are validated strictly before ownership decisions.
- `FullProductReindexer` requires the fence, ledger, recovery, clock, sleeper, and Magento lock manager dependencies. It acquires the fixed rebuild gate before acquiring the durable fence, drains processing claims until the incremental lease plus safety margin, renews around stores and product batches, holds the rebuild gate across ownership proof, alias activation, and exact-token release, and wakes bounded incremental recovery after release.
- `DbIncrementalWorkLedger::claimDueWork()` locks the rebuild-fence row before a product work row and returns no claim while a valid rebuild fence is active. Product-change recording still increments durable generations during the fence for post-cutover replay, and consumed queued wake-ups that encounter the fence are restored to immediately due `pending` state.
- Production row/list/mview scheduling remains the fail-closed `UnavailableIncrementalProductIndexScheduler`; observer/mview capture, reconciliation, and final activation are still deferred.
